# 사진 날짜·장소·인물 태그 자동화 연구 (2026-10-01)

목표: 모든 사진에 **날짜·장소·인물** 태그가 기본으로 붙어 있게 하되, 사람이 한 장씩 손으로 붙이지 않게 한다.
이 문서는 조사 결과와 단계별 구현안이다. 아직 구현하지 않았다. 인물 식별(얼굴 인식)은 이 저장소가
일부러 피해 온 영역이라(`docs/media-performance-and-local-ai.md`: "얼굴 식별·이름 추론은 하지 않는다")
**사용자의 명시적 승인 없이 착수하지 않는다.**

## 1. 지금 이미 되는 것

| 태그 | 언제 붙나 | 근거 코드 |
|---|---|---|
| 날짜 | 업로드 시 자동: 일정 날짜 → EXIF 촬영일(`DateTimeOriginal`) → 업로드일 순 | `src/core/photo-metadata-tags.js` `buildMetadataTags`, `app-image-pipeline.js` (exifr) |
| 장소 | 업로드 시 자동: GPS가 있으면 등록 장소(반경 내) → 역지오코딩 지명 | 같은 파일 `nearestPlaceForCoords`, #93 |
| 모임/일정 | 업로드 시 자동: 그 날짜의 확정 모임 제목·메모 단어 | 같은 함수 |
| 인물 | **자동 없음.** OCR 글자에 참가자 이름이 보일 때만 후보 | `tools/local-media-worker/run-server-photo-analysis.mjs` |
| 추천 검토 | 갤러리 **AI 분석** 탭: iMac M2 워커(macOS Vision)가 장면·OCR·얼굴 *개수*·날짜/장소/일정 후보를 올리고 사용자가 적용/수정/제외 | `ingestMediaAnalysis`, `docs/media-performance-and-local-ai.md` |

## 2. 장소 태그가 자주 빠지는 진짜 이유

**iOS 16.4부터 Safari가 웹 업로드(`<input type=file>`) 사진에서 GPS를 지운다.** 날짜·기종 등 다른 EXIF는
남는다. 아이폰으로 업로드한 사진은 원본에 위치가 있어도 우리 서버에 오는 순간 위치가 없다.
([WebKit bug 257534](https://bugs.webkit.org/show_bug.cgi?id=257534)). 앱 코드로는 막을 수 없다.

대응(쉬운 순):
1. **같은 모임 사진끼리 장소 전파** — 같은 날·같은 업로드 묶음·촬영 시각 ±2시간 안에 GPS가 있는 사진(안드로이드,
   PC 업로드, 카메라)이 하나라도 있으면 나머지 사진에 같은 장소를 *후보*로 제안. 확정 모임에 장소가 지정돼 있으면
   그 장소를 그날 사진 전체 후보로.
2. **구글포토/애플 사진 원본 메타데이터 가져오기** — 아래 3·4번 경로가 위치(geoData)도 함께 준다.
3. PC/맥 브라우저 업로드는 GPS가 유지된다(대량 업로드는 PC에서 하라는 안내 문구).

## 3. 구글포토 인물 분류를 끌어올 수 있나

- **Google Photos API로는 불가.** 2025-03-31부터 라이브러리 전체 읽기 권한(`photoslibrary.readonly` 등)이 폐지돼
  외부 앱은 *자기가 올린 사진*과 사용자가 직접 고르는 **Picker API**만 쓸 수 있다. Picker 결과에도 인물(얼굴 그룹)
  정보는 없다. ([Google 공지](https://developers.google.com/photos/support/updates))
- **Google 테이크아웃(Takeout)으로는 가능.** 구글포토 내보내기의 사진별 JSON 사이드카에
  `"people": [{"name": "서준"}, ...]`(이름을 붙인 얼굴 그룹), `photoTakenTime`, `geoData`가 들어 있다. 얼굴 위치는
  없고 이름 목록만 있다. ([설명](https://metadatafixer.com/learn/google-takeout-json-files-explained),
  [PhotoStructure 문서](https://photostructure.com/guide/people/))

**구현안 A — 테이크아웃 가져오기 (과거 사진 일괄 정리용, 추천)**
1. 사용자가 takeout.google.com에서 Google 포토만 선택해 내보내기 → zip을 iMac의 `Moyeora Inbox/takeout/`에 풀기.
2. M2 워커에 `import-google-takeout` 단계 추가: JSON의 `people`·`photoTakenTime`·`geoData`를 읽고, 같은 폴더의
   이미지로 **지각 해시(pHash)**를 계산해 우리 `photoIndex` 썸네일(이미 내려받는 경로 있음)의 pHash와 매칭.
   - 우리 사진은 WebP로 재압축돼 파일명·EXIF가 원본과 다르므로 파일명 매칭은 쓰지 않는다.
   - 보조 키: 촬영일(날짜 태그) 일치 + 가로세로 비율.
3. 매칭되면 인물·장소·날짜를 **기존 AI 분석 탭의 추천**(`mediaAnalysis`)으로 올린다. 이름은 캘린더 참가자/인물
   태그(`customPersonTags`)와 별칭 매핑표로 맞춘다(예: 구글포토 "박서준" → 우리 "서준").
4. 사용자가 AI 분석 탭에서 "인물 추천 일괄 적용"(신뢰도 높은 것만) 한 번으로 반영. 사진·얼굴 데이터는 맥 밖으로
   나가지 않고, 서버에는 자산 키 + 이름 후보만 올라간다.
- 장점: 이미 구글포토에 붙여 둔 이름을 그대로 재활용, 인식 정확도 = 구글포토 수준.
- 한계: 새로 찍는 사진은 테이크아웃을 다시 해야 한다(월 1회 등). 구글포토에 없는 사진은 매칭 안 됨.

**구현안 A′ — 애플 사진(아이폰 사용자)** 맥의 '사진' 앱 '인물'에 이름이 붙어 있다면, 오픈소스 `osxphotos`가
사진별 인물 이름·위치·촬영 시각을 읽어 준다. 흐름은 A와 동일(맥에서 매칭 → 추천 업로드). iCloud 사진을 쓰면
아이폰 사진도 GPS가 살아 있는 원본 기준이라 **장소 문제(2번)도 같이 해결**된다.

## 4. 새 사진까지 자동으로: 우리만의 얼굴 분류

**구현안 B — 맥(M2)에서 얼굴 묶기 + 한 번만 이름 붙이기**
1. 워커가 새 사진의 얼굴을 찾아(Vision 얼굴 영역) 얼굴 임베딩을 계산한다. 후보 모델: dlib `face_recognition`
   (공개 라이선스, CPU로 충분) 또는 ArcFace 계열 ONNX(정확도↑, 일부 모델은 비상업 라이선스 확인 필요).
2. 비슷한 얼굴끼리 묶고(클러스터링), 앱 **보관함 > 인물**에 "이 사람은 누구인가요?" 카드(얼굴 묶음 + 대표 사진 3장)를
   띄운다. 이름을 한 번 고르면 그 묶음 전체 + 이후 들어오는 같은 얼굴에 **인물 후보**가 자동으로 붙는다.
3. 안 A로 이름이 붙은 사진을 "정답 예시"로 쓰면 처음부터 이름이 붙은 상태로 시작한다.
4. 신뢰도 0.9 이상은 "자동 적용" 옵션(기본 끔), 그 아래는 AI 분석 탭 검토 대기.
- 개인정보: 얼굴 임베딩은 **생체정보(민감정보)**다. 맥 로컬에만 저장하고 서버에는 이름 후보만 올린다. 아이가 포함된
  가족 캘린더라 구성원 동의를 받고, 언제든 "인물 자동 분류 끄기 + 얼굴 데이터 삭제"를 제공한다.
- 클라우드 대안: AWS Rekognition 얼굴 컬렉션(정확도 높음, 사진 1천 장당 약 $1, 사진이 외부로 나감). Google Cloud
  Vision은 얼굴 "검출"만 하고 누구인지 식별하지 않는다. → 기본은 맥 로컬, 클라우드는 비추천.

**보조 규칙 (모델 없이도 큰 효과)**
- 모임 확정 시 고른 **참석자**를 그날 사진의 인물 후보로(얼굴 수와 참석자 수가 맞으면 신뢰도↑).
- 채팅에 사진을 올린 **보낸 사람**은 촬영자 후보(사진 안 인물로는 넣지 않음).

## 4-0. 구현됨: 얼굴 인식 인물 추천 (2026-10-02)

`tools/local-media-worker/face-tags.py` — 구현안 B를 클러스터링 대신 **이미 붙은 인물 태그로 학습**하는 방식으로 구현했다.

- 모델: OpenCV 공식 YuNet(얼굴 찾기) + SFace(얼굴 비교, 128차원), Apache-2.0, 합계 39MB. 처음 실행 때 내려받고
  SHA-256을 확인한다. 설치는 `pip install opencv-python-headless numpy pillow` 하나뿐(dlib 빌드 불필요).
- 학습: 참석자 + 인물 탭 커스텀 인물(customPersonTags)만 대상. "얼굴 1개 + 인물 태그 1개" 사진이 기본 학습 자료이고,
  얼굴 수 = 인물 태그 수인 단체 사진은 1차로 배운 얼굴로 자리를 맞춰 추가 학습한다. 평균에서 먼 표본(잘못 붙은 태그)은 버린다.
  사람당 깨끗한 얼굴 3장 이상이어야 추천을 시작한다.
- 판정: 그 사람의 가장 가까운 얼굴 3개 평균 코사인 ≥ 0.42, 2등과 차이 ≥ 0.06일 때만 추천. 한 얼굴은 한 사람,
  한 사람은 사진당 한 번. 아이처럼 얼굴이 자라는 경우를 위해 평균 하나가 아니라 가까운 표본을 본다.
- 공개 얼굴 데이터(LFW)로 검증: 10명을 가족으로 정하고 사진의 30%에만 태그(그중 3%는 일부러 틀리게),
  모르는 사람 사진 600장을 섞었을 때 — 태그 없는 가족 사진 380장 **100% 맞힘, 다른 이름 0건**, 모르는 사람 600장 중 3장(0.5%)만
  잘못 추천. 태그 10%만 있어도 98% 맞힘, 다른 이름 0건, 오추천 0.3%. (LFW는 정면 성인 사진이라 실제 가족 사진,
  특히 아이 사진은 이보다 낮을 수 있다 → 그래서 자동 적용 없이 고르게 했다.)
- 개인정보: 얼굴 이미지·특징값은 맥의 `~/Library/Application Support/Moyeora/faces/faces.sqlite`에만 있다.
  서버(`ingestMediaAnalysis` kind `faces`)에는 사진 키 + 이름 + 점수만 가고, `mediaAnalysis` 문서의 `facePeople`
  필드에 Vision 결과와 따로 merge 된다. `--disable-schedule --forget`으로 끄고 맥의 얼굴 데이터를 지운다.
- 앱: 보관함 > 추천 > **얼굴로 찾은 사람** 카드(사람별, 확실한 순). 골라서 `#이름 붙이기` 또는 `아니에요`.
  아니에요는 `recordFaceFeedback`으로 그 사진의 `faceRejected`에 남아 다시 추천되지 않는다.
- 자동: `face-tags.py --enable-schedule`이 `media-worker.json`에 `facePython`을 넣으면, 매 사진 분석 실행 뒤
  캘린더마다 `--upload --quiet --max-new 400`으로 돈다. 처음 본 사진만 내려받고 나머지는 저장해 둔 얼굴을 쓴다.

## 4-1. 구현됨: 보관함 "추천" 탭 (2026-10-01)

`src/ui/archive-tag-suggestions.js`(규칙) + `archive-tag-suggestions-view.js`(화면). 보관함 > 추천 탭에서
전체 사진을 읽어 태그 추천을 만들고, 카드마다 [적용], 맨 위 [모두 적용](서버 일괄 명령 한 번 + 되돌리기).

| 규칙 | 근거 | 적용 방식 |
|---|---|---|
| 등록 장소 | 장소 탭이 GPS·같은 업로드 묶음·방문 날짜로 이미 분류했지만 태그는 없는 사진 | 묶음 적용 |
| 같은 날 장소 | 그날 장소 태그가 있는 사진(2장 이상)의 70% 이상이 한 장소 → 그날 카메라 사진·일정 사진 | 묶음 적용 |
| 같은 묶음 공통 태그 | 같은 메시지·같은 날짜 묶음(3장 이상)에서 2장 이상, 태그된 사진의 60% 이상이 가진 태그(날짜·기종·인물 제외) | 묶음 적용 |
| 일정 앨범 날짜 | 날짜 태그가 없는 일정 앨범 사진 → 앨범 날짜(YYMMDD) | 묶음 적용 |
| 같은 날 인물 | 그날 다른 사진에 태그된 사람(실제 쓰인 표기, 예: 서준) | 사진을 골라 이름 탭(자동 적용 없음) |

실데이터 모의 실행(photoIndex 기준): 바로 적용 가능 jhair 169장, cw 248장, kkot 190장. 인물 추천 대상 날짜
jhair 29일(382장), cw 31일(237장), kkot 22일(211장).

### 일괄 적용 기록 (2026-10-01)

사용자 요청("기존 태그를 유지한 채 중복 없이 모두 적용")으로 `npm run ops:apply-tag-suggestions`를 3개 캘린더에
적용했다(직전 `backup-daily` 수동 실행 백업 후). 장소·묶음·앨범 날짜 규칙만 적용, 인물은 사진별 선택이 필요해 제외.

| 캘린더 | 태그 붙인 사진 | 등록 장소 태그가 있는 사진 (전 → 후) |
|---|---|---|
| jhair | 354 | 814 → 926 / 1,532 |
| cw | 261 | 568 → 662 / 1,079 |
| kkot | 220 | 944 → 1,011 / 1,308 |

같은 날 `ops:repair-tag-divergence`로 사본 간 태그 불일치 111장 → 0장. 주의: photoIndex는 쓰기 직후 잠시 늦게
갱신되므로, 일괄 적용 직후에는 반드시 repair dry-run이 0인지 확인한다(인덱스보다 태그가 많은 사본은 되돌리지 않음).

## 5. 추천 진행 순서

| 단계 | 내용 | 효과 | 난이도 |
|---|---|---|---|
| 1 | 장소 전파(같은 날·묶음·모임 장소) + PC 업로드 안내 | 장소 누락 대부분 해결 | 낮음, 앱만 |
| 2 | 구글 테이크아웃(또는 애플 사진) 가져오기 → AI 분석 탭 추천 | 과거 사진 인물·장소·날짜 일괄 | 중간, 맥 워커 |
| 3 | 참석자 기반 인물 후보 | 새 사진 인물 일부 자동 | 낮음 |
| 4 | 맥 얼굴 묶기 + 한 번 이름 붙이기 | 새 사진 인물 자동 | 높음, **승인 필요** |
| 5 | AI 분석 탭 "고신뢰 일괄 적용" | 손 작업 최소화 | 낮음 |

각 단계는 기존 원칙을 지킨다: 사용자 태그가 AI 태그보다 우선, 추천은 덮어쓰지 않고 합침, 태그 저장은
`src/core/media-reference-integrity.js` 규칙(같은 파일의 모든 사본 함께 처리)을 거친다.
