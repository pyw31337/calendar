# 모여라 캘린더 제품 리뉴얼 마스터 기획안

작성일: 2026-09-02  
대상: 사용자용 모여라 캘린더 전체 화면  
목적: 여러 에이전트가 서로의 작업을 망가뜨리지 않고 단계적으로 제품 완성도, 속도, 일관성을 높일 수 있는 실행 기준 제공

---

## 0. 이 문서의 사용법

이 문서는 단순 디자인 제안서가 아니라 작업 지시서다. 각 에이전트는 아래 원칙을 따른다.

1. 작업 시작 전 이 문서와 `docs/design-system.md`, `docs/design-rules.md`, `docs/mobile-checklist.md`, `docs/module-map.md`, `docs/media-asset-ontology.md`, `docs/ops-runbook.md`를 읽는다.
2. 하나의 작업 패키지(WP)는 하나의 명확한 목적과 커밋으로 나눈다.
3. UI 리뉴얼, 데이터 스키마 변경, 성능 리팩터링을 한 커밋에 섞지 않는다.
4. 기존 Firestore 경로와 캘린더 격리 규칙을 UI 개선을 이유로 임의 변경하지 않는다.
5. 다른 에이전트와 같은 파일을 동시에 수정해야 한다면 먼저 담당 범위를 분리한다. `src/core/app-main.js`와 `src/app.css`는 충돌 위험이 가장 높은 파일이다.
6. 각 WP의 완료 조건을 전부 만족하기 전에는 완료로 보고하지 않는다.
7. 배포는 통합 담당자만 수행한다. 개별 에이전트는 임의로 `main`에 직접 푸시하지 않는다.

권장 브랜치명은 `codex/renewal-<wp-id>-<short-name>` 형식이다.

## 1. 현재 문제 정의

### 1.1 한 문장 진단

현재 서비스는 기능이 부족한 것이 아니라, 캘린더·투표·채팅·모임 확정·갤러리·지도가 한 화면에서 비슷한 비중으로 경쟁해 핵심 제품 경험이 흐려져 있다.

### 1.2 라이브 화면에서 확인된 문제

- 390px 모바일 첫 화면에서 캘린더 아래에 투표와 채팅이 즉시 이어지고, 그 아래에 모임 확정·갤러리·지도·푸터가 긴 단일 페이지로 쌓인다.
- 채팅에 포함된 YouTube 영상 하나가 모바일 화면 대부분을 차지해 캘린더보다 더 강한 시각적 주인공이 된다.
- 상단 기능 탭, 섹션 카드, `전체보기`, `더보기`, `펼치기/접기`가 중복되어 사용자가 이동 원리를 학습하기 어렵다.
- 날짜 셀의 작은 점만으로는 어떤 일정인지 알기 어렵고, 캘린더의 핵심 정보 전달력이 낮다.
- 비어 있는 투표도 큰 카드를 차지한다.
- `채팅 59`처럼 숫자의 의미가 전체 개수인지 읽지 않은 개수인지 불분명하다. 읽음 상태 문구와 동시에 노출되면 더 혼란스럽다.
- 거의 모든 영역이 흰색 둥근 카드와 그림자로 감싸져 중요도 차이가 약하다.
- 파랑·보라·초록·빨강 및 이모지 브랜드가 동시에 사용돼 브랜드 중심색과 의미 색상이 섞인다.
- 기능별 로딩·빈 상태·오류·오프라인 표현이 하나의 제품 문법으로 통일되지 않았다.

### 1.3 구조적 원인

- `src/core/app-main.js`가 약 11,000줄, `src/app.css`가 약 5,000줄이며 주요 UI 파일 몇 개에 책임이 과도하게 집중돼 있다.
- 기능이 추가될 때 독립된 목적 화면보다 메인 페이지의 새 섹션으로 붙는 경향이 있다.
- 데이터는 날짜를 중심으로 연결될 수 있지만 화면은 채팅·메모·갤러리·장소라는 저장 출처별 메뉴로 분리되어 있다.
- 공통 모듈은 존재하지만 화면 계층, 상태 문구, 카운터 의미, 미디어 크기 같은 제품 수준 규칙은 충분히 강제되지 않는다.

## 2. 목표 제품 정의

### 2.1 제품 문장

> 모여라 캘린더는 모임의 일정, 결정, 대화, 장소, 사진과 비용을 날짜를 중심으로 연결해 주는 공동 기록 캘린더다.

### 2.2 핵심 사용자 과업

사용자는 앱을 열고 5초 이내에 다음 질문에 답할 수 있어야 한다.

1. 다음 모임은 언제인가?
2. 지금 내가 응답해야 할 투표나 정산이 있는가?
3. 특정 날짜에 무슨 일이 있었는가?
4. 최근 대화나 기록은 무엇인가?
5. 사진·영상·장소·비용이 어느 일정과 연결되는가?

### 2.3 제품 원칙

- **날짜 중심:** 모든 기록은 가능한 한 날짜 또는 모임과 연결한다.
- **점진적 공개:** 홈에는 요약만, 상세 화면에는 전체 기능을 제공한다.
- **한 화면 한 목적:** 한 화면의 주 행동(primary action)은 하나만 명확하게 둔다.
- **상태의 정직성:** 전체 수, 미확인 수, 로드된 수를 섞지 않는다.
- **미디어 절제:** 미디어가 맥락보다 커지지 않게 하며 사용자가 요청할 때 재생한다.
- **빠른 첫 화면:** 캘린더와 가까운 일정이 다른 기능 로딩에 막히지 않아야 한다.
- **안전한 점진 개선:** 데이터 스키마 대수술보다 selector/adapter 계층을 먼저 둔다.

## 3. 성공 지표와 품질 기준

### 3.1 사용자 경험 지표

- 모바일에서 앱 진입 후 캘린더와 다음 일정이 첫 화면 또는 한 번의 짧은 스크롤 안에 보인다.
- 홈에서 전체 페이지를 스크롤하지 않고 채팅·기록·정산으로 이동할 수 있다.
- 날짜 선택 후 일정, 참석, 장소, 대화, 미디어, 정산을 2단계 이내에 열 수 있다.
- 빈 기능은 홈의 큰 카드로 렌더링하지 않는다.
- 카운터에는 `읽지 않음`, `전체`, `표시 중` 중 의미가 명확히 구분된다.

### 3.2 성능 목표

측정은 모바일 3G/저사양 CPU 시뮬레이션과 실제 모바일을 병행한다.

- 핵심 셸과 캘린더는 다른 기능 데이터보다 먼저 상호작용 가능해야 한다.
- 홈 진입 시 채팅 전체, 갤러리 전체, 지도 라이브러리, YouTube iframe을 선로딩하지 않는다.
- 최근 활동은 최대 3~5개 요약만 가져오고 전체 목록은 목적 화면에서 cursor pagination 한다.
- 화면 밖 이미지는 lazy loading, 썸네일 우선, 원본은 상세 진입 후 로드한다.
- 지도는 장소 화면 진입 또는 사용자의 명시적 펼치기 이후에만 마운트한다.
- 동일한 요청을 중복 구독하지 않으며 화면 이탈 시 불필요한 listener를 해제한다.

### 3.3 품질 게이트

모든 통합 커밋은 최소 아래를 통과해야 한다.

```bash
npm run lint:changed
npm run check:design-system
npm run check:design-rules
npm run check:accessibility-safety
npm run check:isolation
npm run safety:test
npm run build
```

배포 후보는 다음을 추가로 통과한다.

```bash
npm run predeploy
npm run smoke:browser:all
npm run smoke:live
```

## 4. 목표 정보 구조

### 4.1 모바일 주 내비게이션

하단 고정 내비게이션을 기본으로 한다.

| 탭 | 목적 | 포함 내용 |
| --- | --- | --- |
| 캘린더 | 날짜와 다음 행동 확인 | 월간 캘린더, 가까운 일정, 응답 필요 항목 |
| 대화 | 사람 간 커뮤니케이션 | 채팅, 댓글, 미확인 대화 |
| 기록 | 모임의 축적된 자료 탐색 | 메모, 사진·영상, 장소, 활동 기록 |
| 정산 | 비용 확인과 처리 | 진행 중 정산, 개인별 잔액, 과거 정산 |
| 더보기 | 저빈도 기능과 환경설정 | 검색, 공유, 기념일, 설정, 도움말, 관리자 진입 |

규칙:

- 현재 탭을 색상과 라벨로 명확히 표시한다.
- 상단의 기존 `투표/채팅/정산/메모` 탭은 하단 내비게이션 도입 후 제거하거나 목적에 맞게 재배치한다.
- 브라우저 뒤로가기는 탭 내부 상세 → 탭 루트 → 이전 브라우저 위치 순으로 예측 가능하게 동작해야 한다.
- 데스크톱은 동일한 목적지를 좌측 또는 상단 내비게이션으로 표현하되 정보 구조는 모바일과 동일하게 유지한다.

### 4.2 캘린더 홈

표시 순서:

1. 브랜드/캘린더 전환/검색/더보기 헤더
2. 월간 캘린더
3. 가까운 일정 1~3개
4. `내가 응답할 일` 영역: 활성 투표, 미정 참석, 미처리 정산만 표시
5. 최근 소식 최대 3개

홈에서 제거할 것:

- 전체 채팅 composer
- 실제 YouTube/Vimeo iframe
- 전체 갤러리 그리드
- 실제 인터랙티브 지도
- 종료된 투표의 상세 결과
- 긴 모임 확정 목록
- 빈 섹션의 큰 카드

홈 요약 카드는 목적 화면으로 이동하는 진입점이어야 하며, 홈 자체에서 모든 작업을 완료하려고 하지 않는다.

### 4.3 날짜 허브(Date Hub)

날짜를 선택하면 해당 날짜가 서비스의 통합 컨텍스트가 된다.

탭 또는 섹션:

- 요약: 일정명, 상태, 참석 현황, 핵심 장소, 정산 요약
- 참여: 참여자 응답과 투표
- 대화: 해당 날짜 태그/모임과 연결된 대화와 댓글
- 기록: 메모, 사진, 영상, 장소 기록
- 정산: 해당 날짜의 지출·수입·개인지출

날짜 허브의 모든 탭은 같은 `selectedDate`와 `meetingId` 컨텍스트를 공유해야 한다. 날짜 문자열 태그(`#YYMMDD`)는 레거시 연결 수단으로 지원하되, 장기적으로 명시적 관계 필드를 우선한다.

### 4.4 기록 화면

기록은 저장 출처보다 탐색 목적을 중심으로 구성한다.

- 전체
- 메모
- 사진·영상
- 장소

공통 필터:

- 날짜 범위
- 사람
- 태그
- 장소
- 모임
- 미디어 유형

각 항목은 출처를 표시하되 출처가 정보 구조의 최상위가 되지 않게 한다.

## 5. 화면별 상세 요구사항

### 5.1 앱 셸과 헤더

- 헤더는 스크롤 중에도 현재 위치와 주요 이동 수단을 잃지 않도록 sticky 동작을 적용한다.
- 모바일 헤더에는 브랜드/캘린더명, 검색, 더보기만 둔다.
- 캘린더명과 서비스 브랜드를 시각적으로 구분한다. `꽃잎반`은 서비스명이 아니라 현재 캘린더명이다.
- 이모지 `🌸`를 계속 사용할 경우 임시 로고임을 명확히 하고, 장기적으로 단색에서도 식별되는 전용 심볼로 교체한다.
- 알림/전체 개수 배지는 목적이 있을 때만 표시한다. 장식용 숫자 배지는 금지한다.

완료 조건:

- 390/430/768/1024/1440px에서 헤더가 깨지지 않는다.
- 하단 내비게이션과 iOS safe-area가 겹치지 않는다.
- 키보드 포커스와 현재 탭 상태를 스크린리더가 인식한다.

### 5.2 월간 캘린더

- 날짜 숫자, 오늘, 선택일, 공휴일, 모임 확정 상태를 서로 다른 방식으로 명확하게 구분한다.
- 작은 점만 표시하지 말고 모바일에서는 최대 1개의 짧은 일정 라벨 또는 유형 아이콘과 `+N`을 사용한다.
- 참여자 색 점은 의미를 알 수 있는 범례 또는 상세 진입 후 설명을 제공한다.
- 셀 전체를 누를 수 있게 하고 최소 터치 영역을 확보한다.
- 월 이동, 오늘 이동, 년월 선택의 아이콘과 hit area를 통일한다.
- 캘린더가 로드되기 전 skeleton은 실제 셀 크기를 유지해 layout shift를 막는다.

### 5.3 가까운 일정과 응답 필요 항목

- 가까운 일정은 날짜, 제목, 장소, 상태, 남은 일수만 간결하게 표시한다.
- 활성 투표가 없으면 큰 빈 카드를 표시하지 않는다.
- 사용자의 응답이 필요한 항목만 `내가 응답할 일`에 나타난다.
- 완료·마감된 항목은 최근 소식 또는 기록 화면으로 이동한다.

### 5.4 채팅

- 홈에서는 최근 메시지 1~3개의 텍스트/썸네일 요약만 보여준다.
- 전체 채팅은 독립 화면에서 제공한다.
- 최초 진입은 최근 메시지 5~20개 범위에서 네트워크 상황에 맞게 제한하고 위로 cursor pagination 한다.
- 새 메시지 구독과 과거 메시지 pagination을 분리한다.
- YouTube/Vimeo는 iframe 대신 썸네일 카드로 먼저 표시하며 사용자가 재생할 때만 player를 마운트한다.
- 세로 영상도 모바일 viewport 높이의 과도한 비율을 차지하지 않도록 preview 최대 높이를 둔다.
- composer는 키보드, safe-area, 이미지 업로드 진행 상태와 겹치지 않는다.
- `59`가 전체 메시지 수인지 미확인 수인지 이름과 스타일을 통해 구분한다.

### 5.5 메모

- 메모는 제목, 요약, 날짜, 작성자, 태그, 연결된 미디어를 일관된 카드 구조로 표시한다.
- 날짜 태그는 파싱된 날짜 링크로 노출하여 날짜 허브로 이동할 수 있게 한다.
- 메모 상세에서 연결된 일정·장소·사진·영상 관계를 한눈에 보여준다.
- 긴 본문과 대형 미디어를 목록에서 직접 전부 렌더링하지 않는다.
- 검색과 필터는 기록 화면의 공통 필터 문법을 재사용한다.

### 5.6 사진·영상과 갤러리

- `docs/media-asset-ontology.md`의 canonical asset 원칙을 유지한다.
- 사진과 영상은 하나의 미디어 자산 목록으로 다루되 유형 필터를 제공한다.
- 날짜 허브에서는 영상 묶음을 사진 위에 별도 표시할 수 있다.
- 목록은 썸네일만 로드하고 원본은 lightbox/player 진입 후 로드한다.
- 중복 자산은 `sourceMessageId/sourceImageIndex`, `mediaKey/refKey`로 통합한다.
- 태그 수정과 삭제는 어느 화면에서 실행하든 같은 canonical asset에 반영된다.
- 깨진 썸네일, 삭제된 원본, 외부 영상 접근 실패에 공통 fallback을 제공한다.

### 5.7 장소와 지도

- 홈에는 지도 자체가 아니라 `장소명 + 간단 주소 + N개 장소 보기` 요약만 둔다.
- 지도 라이브러리와 타일은 장소 화면 또는 사용자의 명시적 지도 열기 후 로드한다.
- 기본 지도는 밝은 모노톤을 유지하되 도로·지역명·주요 지형 라벨을 읽을 수 있어야 한다.
- 키 오류나 타일 장애가 발생해도 장소 목록과 외부 지도 링크는 계속 사용할 수 있어야 한다.
- 장소는 방문일, 관련 모임, 메모, 사진과 연결한다.

### 5.8 정산

- 홈에는 `내가 낼 돈/받을 돈`과 미처리 상태만 요약한다.
- 상세 화면에서만 전체 지출·수입·개인지출과 편집 기능을 제공한다.
- 금액 색상은 수입/받을 돈, 지출/낼 돈, 완료 상태의 의미를 일관되게 사용한다.
- 기존 `docs/design-system.md`의 정산 특칙을 유지한다.
- 데이터가 없는 캘린더에서는 빈 정산 섹션을 홈에 표시하지 않는다.

### 5.9 투표

- 투표는 독립된 상시 최상위 탭보다 `응답이 필요한 작업`으로 취급한다.
- 활성 투표만 홈에 노출하고 종료된 투표는 기록 또는 날짜 허브에 둔다.
- 투표 카드에는 마감, 내 응답 여부, 전체 참여 상태를 먼저 보여준다.
- 후보 추가·중복 투표 같은 상세 규칙은 보조 정보로 내린다.

### 5.10 메뉴와 설정

- 메뉴에는 저빈도 이동과 환경설정만 둔다.
- 사용자에게 내부 구현 개념(푸시 구독 레코드, 등록 기기 ID 등)을 노출하지 않는다.
- 알림 설정은 `알림 허용`과 채팅·메모·투표·일정 채널만 명확하게 제공한다.
- 글자 크기, 테마, 알림은 즉시 결과를 확인할 수 있어야 한다.
- 관리자 기능은 일반 사용자 기능과 시각·권한상 명확하게 분리한다.

### 5.11 공통 상태 화면

각 기능은 다음 5개 상태를 반드시 정의한다.

1. 초기 로딩: 실제 레이아웃과 비슷한 skeleton
2. 점진 로딩: 기존 콘텐츠를 유지한 채 추가 로드 표시
3. 빈 상태: 이유와 가능한 다음 행동 1개
4. 오류 상태: 짧은 설명, 재시도, 대체 경로
5. 오프라인 상태: 마지막 확인 시점, 쓰기 대기 여부, 재연결 동작

오래된 캐시를 새 데이터처럼 보이지 않게 한다. 캐시를 표시한다면 `마지막 업데이트`와 동기화 상태를 함께 표시하고 백그라운드 재검증을 수행한다.

## 6. 시각 디자인 시스템 개편

### 6.1 색상

- 브랜드 주색상은 한 계열로 제한한다. 권장: 깊은 인디고/블루 1계열.
- 초록은 성공·정산 수입, 빨강은 오류·위험·공휴일, 주황은 경고로 의미를 고정한다.
- 참여자 고유색은 데이터 표현에만 사용하고 글로벌 액션 색상으로 사용하지 않는다.
- 텍스트 대비는 WCAG AA를 기준으로 한다.

### 6.2 타이포그래피

- 화면 제목, 섹션 제목, 본문, 보조 문구, 캡션의 5단계만 우선 사용한다.
- `font-weight: 900/950` 남용을 줄이고 400/500/600/700 중심으로 정리한다.
- 숫자 배지와 메타 정보가 본문보다 강하게 보이지 않게 한다.
- 모바일 본문과 입력은 읽기 가능한 크기 및 기존 16px 입력 규칙을 유지한다.

### 6.3 표면과 카드

- 모든 섹션을 카드로 만들지 않는다. 동일 화면 내 연속 콘텐츠는 여백과 divider로 구분한다.
- 그림자는 overlay, floating navigation, drag surface처럼 실제 높이 차이가 있는 요소에만 사용한다.
- 외곽 10px, 내부 6px 규칙은 유지하되 무조건적인 둥근 박스 생성을 금지한다.
- 한 화면에서 primary button은 원칙적으로 하나만 강하게 표시한다.

### 6.4 아이콘과 모션

- 같은 의미에 하나의 아이콘을 사용한다.
- 장식 이모지는 브랜드/콘텐츠를 제외하고 기능 아이콘으로 사용하지 않는다.
- 모션은 상태 변화 설명에만 사용하며 `prefers-reduced-motion`을 지원한다.
- hover 전용 정보 없이 터치·키보드에서도 동일한 정보를 제공한다.

## 7. 데이터 온톨로지와 연결 구조

### 7.1 목표 개념 모델

```text
Calendar
 ├─ Member
 ├─ DayContext(date)
 │   ├─ Event / ConfirmedMeeting
 │   ├─ ActionItem(Poll, Attendance, Settlement)
 │   ├─ ConversationRef
 │   ├─ MemoRef
 │   ├─ MediaAssetRef
 │   ├─ PlaceRef
 │   └─ SettlementRef
 └─ Activity
```

### 7.2 구현 원칙

- 첫 단계에서는 Firestore 스키마를 바꾸지 않는다.
- 기존 컬렉션을 날짜 허브에 맞게 합성하는 selector/adapter를 만든다.
- 명시적 `date`, `meetingId`, `relatedEntityIds`가 있으면 우선 사용한다.
- 레거시 `#YYMMDD` 태그는 fallback 관계로 해석한다.
- 관계를 저장하는 새 필드가 필요하면 읽기 호환 → 이중 쓰기 → backfill → 구형 fallback 제거 순서의 별도 마이그레이션 계획을 세운다.
- 미디어는 기존 canonical asset 규칙을 절대 깨지 않는다.

### 7.3 권장 selector

- `getDayContext(calendarId, date)`
- `getUpcomingEvents(calendarId, now, limit)`
- `getPendingActions(calendarId, participantId)`
- `getRecentActivitySummary(calendarId, limit)`
- `getRelatedRecords(entityType, entityId)`
- `getMediaForDay(calendarId, date, type)`

selector는 가능한 한 순수 함수로 만들고 fixture 기반 테스트를 추가한다.

## 8. 프론트엔드 구조 개선 원칙

### 8.1 목표 디렉터리 예시

```text
src/
 ├─ app/                 # route, app shell, navigation
 ├─ features/
 │   ├─ calendar/
 │   ├─ day-context/
 │   ├─ chat/
 │   ├─ records/
 │   ├─ media/
 │   ├─ places/
 │   ├─ settlement/
 │   └─ settings/
 ├─ entities/            # calendar/member/event/media/place 등 모델과 selector
 ├─ services/            # Firebase, upload, notification, map
 ├─ shared/
 │   ├─ ui/
 │   ├─ hooks/
 │   ├─ styles/
 │   └─ utils/
 └─ main.jsx
```

### 8.2 점진 분리 규칙

- `app-main.js` 전체 재작성은 금지한다.
- 새 앱 셸과 새 화면은 별도 모듈로 만들고 기존 기능을 adapter로 호출한다.
- 한 번에 하나의 route/view만 이동한다.
- `window.GATHER_*` 의존성을 새 모듈에 추가하지 않는다. 기존 의존성은 얇은 adapter 뒤로 숨긴다.
- CSS는 기능별 파일 또는 cascade layer로 분리하며 전역 selector 추가를 최소화한다.
- 디자인 토큰은 단일 파일을 기준으로 하고 하드코딩 색상 증가를 막는 검사를 추가한다.

## 9. 에이전트 작업 패키지

각 WP에는 산출물, 예상 파일, 선행조건, 완료 기준이 있다. 여러 에이전트가 병렬 작업할 때 같은 단계 안에서도 파일 충돌 여부를 먼저 확인한다.

### WP-00 기준선과 회귀 캡처

담당: QA/통합 에이전트  
선행조건: 없음

작업:

- 라이브와 로컬의 390, 430, 768, 1024, 1440px 핵심 화면 상태를 기록한다.
- 캘린더, 날짜 팝업, 채팅, 메모, 갤러리, 장소, 정산, 설정의 smoke 시나리오를 목록화한다.
- 성능 기준선: 초기 요청 수, 전송량, 주요 chunk, 첫 상호작용 가능 시점, 지도/iframe 선로드 여부를 측정한다.
- 기존 주요 데이터 경로와 캘린더 격리 테스트를 확인한다.

산출물:

- `docs/renewal-baseline.md`
- 필요한 경우 `scripts/product-renewal-smoke.mjs`

완료 기준:

- 개선 전/후를 같은 조건으로 비교할 수 있다.
- 쓰기 테스트는 전용 테스트 캘린더에서만 수행한다.

### WP-01 제품 셸과 라우팅 상태 모델

담당: 앱 셸 에이전트  
선행조건: WP-00

작업:

- 목표 탭 5개의 route/state 규약을 설계한다.
- 브라우저 뒤로가기, deep link, 공유 URL 호환 규칙을 작성한다.
- 모바일 하단 내비게이션과 데스크톱 대응 내비게이션을 구현한다.
- 기존 상단 4개 기능 탭은 기능 플래그 뒤에서 새 내비게이션으로 대체한다.
- 기존 공유 URL과 날짜 팝업 링크가 깨지지 않게 adapter를 둔다.

예상 파일:

- `src/core/app-main.js`의 route/view 부분
- 신규 `src/ui/ui-app-shell.js` 또는 `src/app/`
- `src/app.css` 또는 신규 shell CSS
- route 관련 검사 스크립트

완료 기준:

- 모든 탭에 direct URL로 진입 가능하다.
- 새로고침과 뒤로가기가 화면 상태를 잃지 않는다.
- 기존 공유 URL 검사가 통과한다.

### WP-02 디자인 토큰과 공통 상태 컴포넌트

담당: 디자인 시스템 에이전트  
선행조건: WP-00, WP-01 인터페이스 합의

작업:

- 브랜드/semantic/participant 색상의 역할을 분리한다.
- 타이포그래피 5단계, spacing, divider, elevation 규칙을 토큰화한다.
- `LoadingState`, `EmptyState`, `ErrorState`, `OfflineState`, `SectionHeader`, `CountBadge`를 공통화한다.
- 카운터 유형을 `total`, `unread`, `pending`, `visible`로 명시한다.
- reduced motion, focus ring, AA 대비를 검수한다.

완료 기준:

- 신규 화면은 하드코딩 색상 없이 주요 상태를 표현한다.
- 공통 상태의 문구와 버튼 구조가 모든 기능에서 재사용 가능하다.
- 기존 디자인 검사와 접근성 검사가 통과한다.

### WP-03 캘린더 홈 재구성

담당: 캘린더 UX 에이전트  
선행조건: WP-01, WP-02

작업:

- 홈을 캘린더, 가까운 일정, 응답 필요, 최근 소식으로 재구성한다.
- 기존 채팅/갤러리/지도 전체 섹션을 홈에서 제거하고 요약 진입점으로 바꾼다.
- 활성 데이터가 없으면 빈 큰 카드를 숨긴다.
- 캘린더 셀 일정 라벨/`+N` 표시와 skeleton을 구현한다.
- 기존 일정 등록·수정·삭제 동작은 유지한다.

예상 파일:

- `src/ui/ui-calendar-core.js`
- `src/ui/ui-summary-gallery.js`
- 신규 home summary 모듈
- 관련 CSS

완료 기준:

- 390px 첫 화면에서 캘린더가 주인공으로 보인다.
- YouTube iframe과 지도 라이브러리가 홈 진입만으로 로드되지 않는다.
- 일정 데이터가 많은 달에도 셀 레이아웃이 깨지지 않는다.

### WP-04 날짜 허브와 selector 계층

담당: 날짜/온톨로지 에이전트  
선행조건: WP-03, 관계 규칙 합의

작업:

- `getDayContext` 계열 순수 selector와 fixture 테스트를 만든다.
- 기존 날짜 팝업을 요약/참여/대화/기록/정산 구조로 재편한다.
- `#YYMMDD` 태그, 명시적 날짜, meeting 참조의 우선순위를 구현한다.
- 사진과 영상은 미디어 유형별로 구분하되 동일 canonical asset을 사용한다.
- 탭 전환 시 같은 날짜 컨텍스트를 유지한다.

완료 기준:

- 일정·참여·메모·영상·사진·장소·정산이 같은 날짜 기준으로 일치한다.
- 레거시 데이터도 누락 없이 표시된다.
- selector 테스트가 Firestore 없이 실행 가능하다.

### WP-05 채팅 독립 화면과 미디어 절제

담당: 채팅 에이전트  
선행조건: WP-01, WP-02

작업:

- 홈 채팅 preview와 전체 채팅 화면을 분리한다.
- 최초 최근 메시지 제한, 위쪽 cursor pagination, 실시간 새 메시지 구독을 분리한다.
- 영상은 클릭 전 썸네일 카드로 렌더링한다.
- composer, 업로드, 오프라인 대기, 재시도 상태를 정리한다.
- 읽지 않은 수와 전체 수를 분리한다.

예상 파일:

- `src/ui/ui-chat-room.js`
- `src/core/app-chat-data.js`
- `src/core/app-firebase-data.js`
- 미디어 공통 컴포넌트

완료 기준:

- 저속망에서 최근 메시지가 먼저 보인다.
- iframe은 사용자 재생 시점 전에는 생성되지 않는다.
- 과거 메시지 추가 로드 중 현재 scroll anchor가 유지된다.

### WP-06 기록 허브: 메모·미디어·장소

담당: 기록 에이전트  
선행조건: WP-01, WP-02, WP-04 selector 인터페이스

작업:

- 전체/메모/사진·영상/장소 탭을 만든다.
- 날짜·사람·태그·모임·유형 공통 필터를 구현한다.
- 목록은 요약과 썸네일만 렌더링하고 상세에서 전체를 보여준다.
- 날짜와 관련 엔티티 링크를 제공한다.
- 기존 메모/갤러리/장소 direct URL을 새 탭으로 매핑한다.

완료 기준:

- 동일 자산 중복 표시가 줄어든다.
- 필터 변경이 URL 또는 복원 가능한 상태에 반영된다.
- 기존 편집·삭제 권한과 확인 절차가 유지된다.

### WP-07 정산 화면 재배치

담당: 정산 에이전트  
선행조건: WP-01, WP-02

작업:

- 홈 요약과 정산 전체 화면을 분리한다.
- 개인 관점의 낼 돈/받을 돈/완료 상태를 우선 표시한다.
- 기존 정산 등록·수정·삭제·마감 로직은 변경하지 않고 표현 계층만 재배치한다.
- 날짜 허브와 정산 상세의 연결을 추가한다.

완료 기준:

- 정산이 없는 사용자의 홈에는 큰 빈 영역이 없다.
- 기존 계산 fixture와 쓰기 safety 테스트가 통과한다.
- 수입/지출 부호와 색상 의미가 전 화면에서 일치한다.

### WP-08 메뉴·설정·검색 정리

담당: 설정/탐색 에이전트  
선행조건: WP-01, WP-02

작업:

- 더보기 탭에 검색, 공유, 기념일, 설정, 도움말을 정리한다.
- 내부 기술 개념을 사용자 UI에서 제거한다.
- 검색 결과를 날짜/대화/메모/미디어/장소 유형으로 일관되게 표시한다.
- 테마·글자 크기·알림 설정의 즉시 피드백과 오류 상태를 통일한다.

완료 기준:

- 중복 메뉴 진입점이 없다.
- 설정 변경 후 결과와 저장 상태를 사용자가 이해할 수 있다.
- 관리자 진입은 일반 사용자 기능과 구분된다.

### WP-09 성능과 구독 수명주기

담당: 성능 에이전트  
선행조건: WP-03~WP-08 화면 계약 확정

작업:

- 탭별 dynamic import와 데이터 구독 시작/해제를 정리한다.
- 홈에서 채팅 전체, 갤러리 전체, 지도, player chunk가 로드되지 않게 한다.
- 이미지 thumbnail/srcset/lazy/decoding 전략을 통일한다.
- cursor pagination과 중복 요청 방지를 공통 hook/service로 만든다.
- 캐시 사용 시 stale 표시와 background revalidation을 분명히 한다.
- 느린 3G와 구형 기기에서 long task, 메모리, listener 수를 측정한다.

완료 기준:

- WP-00 기준선 대비 초기 요청과 전송량이 감소한다.
- 탭 이동을 반복해도 listener와 timer가 누적되지 않는다.
- 오래된 데이터를 최신처럼 표시하지 않는다.

### WP-10 접근성·반응형·브라우저 호환

담당: 접근성 QA 에이전트  
선행조건: 각 화면 WP의 통합 후보

작업:

- 키보드만으로 주요 흐름을 수행한다.
- dialog focus trap, 복귀 포커스, aria label, live region을 확인한다.
- 200% 글자 확대와 큰 글자 설정을 점검한다.
- 390/430/768/1024/1440px 및 Safari/Chrome/Firefox/Whale 계열을 점검한다.
- iOS safe-area, 가상 키보드, Android 뒤로가기를 검수한다.
- 색상만으로 상태를 구분하지 않는지 확인한다.

완료 기준:

- 핵심 흐름에 키보드 trap이 없다.
- 터치 대상과 텍스트 대비 기준을 충족한다.
- 모바일 체크리스트가 전부 갱신되고 체크된다.

### WP-11 코드 모듈화와 기술부채 축소

담당: 아키텍처 에이전트  
선행조건: 신규 화면 경계 안정화

작업:

- `app-main.js`에서 route/view 단위로 작은 모듈을 이동한다.
- 기능별 CSS와 공통 토큰을 분리한다.
- 새 코드의 `window.GATHER_*` 의존성 생성을 막는다.
- 순수 selector와 service adapter의 테스트를 늘린다.
- 아키텍처 budget을 갱신하되 단순히 한도를 늘려 검사를 통과시키지 않는다.

완료 기준:

- 추출 전후 동작이 동일하다.
- 한 커밋에 1개 모듈 경계만 변경한다.
- 전역 심볼과 순환 의존성이 증가하지 않는다.

### WP-12 통합, 점진 출시, 배포

담당: 통합/릴리스 에이전트  
선행조건: 모든 필수 WP 완료

작업:

- 기능 플래그로 신규 셸을 내부/특정 테스트 캘린더에 먼저 노출한다.
- 기존 화면과 신규 화면의 데이터 결과를 비교한다.
- predeploy, 브라우저 smoke, 라이브 smoke를 수행한다.
- 배포 전 복구 태그와 rollback 절차를 확인한다.
- 메인 배포 후 모바일과 데스크톱 라이브에서 핵심 흐름을 직접 확인한다.
- 오류율, 로딩 실패, 콘솔 오류, Firestore 읽기량을 관찰한다.

완료 기준:

- `main`과 원격 SHA가 일치한다.
- GitHub Pages Deploy와 Verify/live-smoke가 성공한다.
- 라이브에서 캘린더, 날짜 허브, 채팅, 기록, 정산, 설정을 점검한다.
- 심각한 회귀가 있으면 즉시 기능 플래그 또는 이전 안정 태그로 복구할 수 있다.

## 10. 권장 단계와 병렬화

### Phase A: 기준과 기반

`WP-00 → WP-01 → WP-02`

WP-01과 WP-02는 인터페이스를 먼저 합의한 뒤 일부 병렬 진행할 수 있다. 이 단계에서는 기존 기능 위치를 대규모로 옮기지 않는다.

### Phase B: 핵심 경험

`WP-03 → WP-04`

캘린더 홈과 날짜 허브가 제품의 중심이다. 이 두 작업은 먼저 완성하고 사용자 경험 기준을 고정한다.

### Phase C: 목적 화면

`WP-05, WP-06, WP-07, WP-08`

화면별 파일 소유권이 겹치지 않으면 병렬 진행할 수 있다. 공통 셸, 토큰, selector 계약은 임의 변경하지 않는다.

### Phase D: 횡단 품질

`WP-09, WP-10, WP-11`

성능과 접근성은 마지막 장식 작업이 아니다. 각 화면 통합 시점부터 반복 측정하고, 최종 단계에서는 전역 회귀를 수행한다.

### Phase E: 출시

`WP-12`

한 번에 전 사용자에게 전환하지 않고 테스트 캘린더 → 일부 사용자 → 전체 순으로 확대한다.

## 11. 에이전트 간 계약

각 에이전트는 완료 보고에 다음을 포함한다.

1. 변경 목적과 사용자 영향
2. 변경 파일 목록
3. 데이터 경로 또는 public interface 변경 여부
4. 수행한 자동 테스트와 결과
5. 수동 확인한 viewport/브라우저/시나리오
6. 알려진 제한과 후속 작업
7. 커밋 SHA

공통 interface를 바꿀 때는 다음을 지킨다.

- 호출부를 찾지 않고 함수 시그니처를 바꾸지 않는다.
- selector 반환 구조를 변경하면 fixture와 모든 소비 화면을 함께 갱신한다.
- CSS class 제거 전 `rg`로 전체 소비처를 확인한다.
- Firestore write path 변경은 별도 승인과 migration/rollback 계획 없이는 금지한다.
- 공통 파일의 대규모 formatter 변경을 기능 커밋에 섞지 않는다.

## 12. 금지 사항

- 메인 홈에 새 대형 섹션을 추가하는 방식으로 문제를 해결하지 않는다.
- 상용서비스 느낌을 내기 위해 그림자, gradient, animation을 더하지 않는다.
- 모든 데이터를 처음부터 한 번에 가져오지 않는다.
- 카운터에 서로 다른 의미의 숫자를 같은 스타일로 표시하지 않는다.
- 영상 iframe을 목록과 홈에서 자동 마운트하지 않는다.
- 캐시 데이터를 갱신 시점 표시 없이 최신 데이터처럼 보여주지 않는다.
- UI 리뉴얼과 Firestore 스키마 변경을 같은 배포에 넣지 않는다.
- 기존 미디어 canonical asset을 화면별 복사본으로 분리하지 않는다.
- 안전 테스트를 삭제하거나 한도만 늘려 회귀를 숨기지 않는다.
- 라이브 데이터로 파괴적 테스트를 하지 않는다.

## 13. 최종 출시 체크리스트

### 제품

- [ ] 홈의 첫 인상이 캘린더 중심이다.
- [ ] 사용자가 응답해야 할 항목이 명확하다.
- [ ] 날짜 허브에서 관련 데이터가 한 맥락으로 연결된다.
- [ ] 채팅, 기록, 정산이 독립된 목적 화면으로 동작한다.
- [ ] 메뉴와 설정에 내부 기술 개념이 없다.

### 디자인

- [ ] 브랜드 주색상과 semantic 색상 역할이 분리됐다.
- [ ] 카드, 그림자, 굵은 글씨가 과도하지 않다.
- [ ] 카운터 의미가 명확하다.
- [ ] 미디어가 화면을 과도하게 점유하지 않는다.
- [ ] 빈/로딩/오류/오프라인 상태가 통일됐다.

### 성능

- [ ] 홈에서 지도와 영상 player를 선로드하지 않는다.
- [ ] 최근 데이터 우선 + cursor pagination이 동작한다.
- [ ] 화면 이탈 후 listener/timer가 정리된다.
- [ ] 이미지가 썸네일·lazy 전략을 따른다.
- [ ] 느린 3G와 구형 모바일 기준선을 재측정했다.

### 안정성

- [ ] 캘린더별 데이터 격리가 유지된다.
- [ ] 기존 공유 URL과 deep link가 유지된다.
- [ ] 사진·영상 canonical asset 규칙이 유지된다.
- [ ] 정산 계산과 쓰기 안전 검사가 통과한다.
- [ ] rollback 태그와 절차가 준비됐다.

### 배포

- [ ] `npm run predeploy` 통과
- [ ] `npm run smoke:browser:all` 통과
- [ ] GitHub Actions Deploy/Verify/live-smoke 성공
- [ ] 라이브 모바일·데스크톱 직접 확인
- [ ] 원격 `main` SHA와 배포 build SHA 일치

## 14. 최우선 착수 순서

리소스가 제한되면 아래 6개만 먼저 진행한다.

1. WP-00 기준선과 회귀 캡처
2. WP-01 모바일 하단 내비게이션과 앱 셸
3. WP-02 상태/카운터/타이포그래피 공통 규칙
4. WP-03 캘린더 중심 홈과 대형 섹션 제거

6. WP-05 영상 지연 마운트와 채팅 독립 화면

이 6개가 완료되면 기능 수를 줄이지 않고도 서비스의 첫 인상, 이해 가능성, 체감 속도, 일관성이 가장 크게 개선된다.
