# 모여라 캘린더 디자인 리뉴얼 — 통합 인계 문서

**이 문서는 누구를 위한 것인가:** 이 리뉴얼 작업이 중단된 뒤 Claude가 아닌 다른 에이전트(Codex,
Grok, Gemini 등 무엇이든)가 이어받더라도, 이 문서 하나만 처음부터 끝까지 읽으면 (1) 지금까지
무엇이 결정됐고 왜 그렇게 됐는지, (2) 실제로 무엇이 코드로 반영됐는지, (3) 무엇이 아직 시안
단계인지, (4) 절대 빠뜨리면 안 되는 기존 기능이 무엇인지, (5) 다음에 뭘 해야 하는지를 전부 알 수
있게 쓴다. 특정 AI 도구 이름이나 세션 ID에 의존하는 설명은 넣지 않는다 — 이 저장소와 문서만
보고 재현 가능해야 한다.

작성 기준일: 2026-09-13.

---

## 0. 읽는 순서

1. 이 문서 (전체 그림 + 인계 사항)
2. `docs/product-renewal-master-plan.md` — 리뉴얼의 "왜"와 "무엇을" 정의한 마스터 기획안. 모든
   설계 결정의 최종 근거는 이 문서다. 이 문서와 마스터플랜이 충돌하면 **마스터플랜이 우선**한다.
3. `docs/renewal-baseline.md` — WP-00 산출물. 리뉴얼 시작 시점의 실제 화면/성능/코드량 기준선.
4. `docs/wp01-app-shell-progress.md` — WP-01(신규 앱 셸) 실제 코드 작업 진행 로그.
5. `docs/page-feature-contract.md` — 각 화면이 소유한 데이터와 지켜야 할 불변조건. 리뉴얼 중
   어떤 화면을 어떻게 재배치하든 이 계약은 깨면 안 된다.
6. `CLAUDE.md` (저장소 루트) — 이 저장소에서 절대 하면 안 되는 것들 (캘린더 격리, JSONBlob/
   localStorage 금지, `assets/*` 오해 금지 등). 코드를 한 줄이라도 건드리기 전에 반드시 읽는다.

이 문서 자체를 갱신할 때도 위 5개 문서와 모순이 생기지 않는지 다시 확인한다.

## 1. 전체 그림 — 지금 이 리뉴얼은 두 갈래로 진행 중이다

### 1.1 갈래 A: 디자인 시안 (Claude Design 캔버스, 코드 아님)

프로덕션 코드와 완전히 분리된 별도의 시각 디자인 탐색 산출물이다. 반응형 정보 밀도, 사이드
메뉴, 게이미피케이션 요소 등 "이렇게 보이면 좋겠다"를 눈으로 확인하기 위해 만든 것이고,
**여기 담긴 어떤 코드도 프로덕션에 그대로 복사-붙여넣기 하면 안 된다** (섹션 2 참고 — 실제로
이 시안의 사이드바 구조는 마스터플랜과 어긋나서 폐기 방향으로 결정됐다).

- 게시된 링크: `https://claude.ai/code/artifact/db94ed3b-d4ce-4d8c-9072-a71c9927bd18` (Claude
  계정 로그인이 있어야 열린다. 로그인 계정이 다른 도구/에이전트라면 이 링크 자체보다는 아래
  "무엇이 들어있는지" 요약과, 실제 소스가 남아있다면 세션 스크래치 디렉터리의
  `BentoPinkFinal.dc.html` 등 `.dc.html` 파일들을 참고한다 — 단, 스크래치 디렉터리는 세션이
  끝나면 사라질 수 있으므로 영구 보존이 필요한 결정/근거는 전부 이 문서와 아래 커밋들에 옮겨
  적었다.)
- 형식: `.dc.html` 아트보드 16개가 한 캔버스에 나열된 것. 실제 React 코드가 아니라 정적/의사
  인터랙티브 HTML 목업이다 (자체 `DCLogic` 클래스 기반 상태 관리, `React.createElement`가 아닌
  템플릿 바인딩 `{{}}` 문법 사용 — 프로덕션 코드 스타일과 다르다).

  WP-02에서 마스터플랜 기준으로 다시 정해야 한다. 시안의 보라색은 확정이 아니라 참고 후보.
- 기념일(핑크 계열 #EC4899/#F472B6/#BE185D)은 브랜드 액센트와 별도로 유지해야 한다는 것을 이번
  세션에서 여러 번 재확인함 — 색상 일괄 변경(sed) 시 실수로 같이 바뀐 적이 있어서, WP-02
  작업자는 반드시 참여자 고유색·기념일색·브랜드색 세 계열을 처음부터 분리해서 토큰화할 것.
- 캘린더 셀의 "정보량이 화면 폭에 따라 늘어나는" 패턴: 실제 `app.css`에 이미 있는
  `.day-corner-label`/`.date-year`(640px 이상 노출), `.gallery-thumb-grid`(1024px 6열) 패턴을
  그대로 따라 한 것 — 이건 시안이 아니라 **이미 실제 프로덕션에 있는 규칙**이므로 새로 만들
  필요 없이 재사용하면 된다.
- 참여자 점(`.p-dot`)에 이름 텍스트를 캡슐 형태로 넣는 것, 기념일 바에 라벨 텍스트를 넣는 것은
  아직 프로덕션에 없는 신규 아이디어 — 실제로 넣을지는 WP-03(캘린더 홈 재구성)에서 판단.
- "댓글 달린 썸네일 반짝임"과 "모임확정 게이미피케이션 버튼"은 **시안이 아니라 실제
  프로덕션에 이미 있는 기능**을 그대로 시안에 옮겨온 것 — 섹션 3.9 참고. 즉 이 두 개는
  "새로 만들 것"이 아니라 "리뉴얼 후에도 절대 빠뜨리면 안 되는 것" 목록에 들어간다.

## 2. IA(정보 구조) 결정: 마스터플랜의 5탭 구조로 확정

이번 세션 중 가장 중요한 방향 전환이 있었다: 위 1.1 갈래 A(디자인 시안)는 초기에 **기존
저장소별 6개 메뉴(캘린더/채팅/메모/갤러리/장소/정산)를 그대로 사이드바로 옮긴 구조**로
만들어졌다. 그런데 `docs/product-renewal-master-plan.md` §4.1을 다시 확인해보니 이미 명확한
목표 IA가 있었다:

> 하단 고정 내비게이션 5탭: **캘린더 / 대화 / 기록 / 정산 / 더보기**
> "기존 상단 4개 기능 탭(투표/채팅/정산/메모)은 기능 플래그 뒤에서 새 내비게이션으로 대체한다."
> "데스크톱은 동일한 목적지를 좌측 또는 상단 내비게이션으로 표현하되 정보 구조는 모바일과
> 동일하게 유지한다."

레포지토리 소유자에게 확인한 결과 **마스터플랜의 5탭 구조를 따르기로 확정**했다. 즉:

- 시안(갈래 A)의 6메뉴 사이드바 정보구조는 **폐기**한다. 시각적 디테일(글래스 버튼, 접기/펼치기
  인터랙션 등)만 참고 가치가 있다.
- "기록" 탭 하나가 기존에 흩어져 있던 **메모 + 갤러리(사진·영상) + 장소 + 보관함(추억) +
  콘텐츠**를 전부 흡수한다 — 이 다섯 개 전부다. `docs/page-feature-contract.md`의 화면 목록에
  9개 화면(캘린더/채팅/갤러리/장소/메모/정산/보관함/콘텐츠/검색·공유·설정)이 있는데, 초기에는
  "메모/갤러리/장소 3개만 기록으로"라고 잘못 축약했었다 — **보관함(추억)과 콘텐츠(지역축제 등)를
  빠뜨리면 안 된다.** 이 두 개도 "기록" 탭 안의 서브탭으로 들어가야 한다.
- "투표"는 마스터플랜 §5.9에 따라 독립 탭이 아니라 캘린더 홈의 "내가 응답할 일" 섹션에
  녹아든다 (활성 투표만, 마감/응답여부/전체 참여 상태 우선 표시).
- "정산"은 그대로 독립 탭 유지.
- "검색/공유/기념일설정/앱설정/도움말/관리자 진입"은 전부 "더보기" 탭 안으로 들어간다
  (마스터플랜 §5.10). 단, 검색은 헤더에도 바로가기 아이콘을 하나 더 둔다 (§5.1) — 이건 이미
  WP-01 1차 슬라이스에 반영함 (섹션 4 참고).

**5탭과 기존 9개 화면(page-feature-contract.md 기준) 매핑표 — 다음 작업자는 이 표를 기준으로
빠진 화면이 없는지 항상 재확인할 것:**

| 새 탭 | 흡수하는 기존 화면 | 비고 |
| --- | --- | --- |
| 캘린더 | 캘린더/메인 | 투표는 여기 "응답할 일" 섹션으로 |
| 대화 | 채팅 | |
| 기록 | 메모, 갤러리, 장소, 보관함(추억), 콘텐츠 | **5개 전부.** 서브탭 또는 필터로 구현 (마스터플랜 §4.4 "전체/메모/사진·영상/장소" 예시는 3개뿐이지만 실제 화면 목록엔 보관함·콘텐츠도 있으므로 §4.4 예시에 이 둘을 추가해서 구현해야 함) |
| 정산 | 정산 | |
| 더보기 | 검색(+헤더 바로가기), 공유, 기념일 설정, 캘린더 설정, 앱 설정(테마/글자크기/알림), 사용자 매뉴얼, 관리자 진입 | 마스터플랜 §5.10 |

**실제 프로덕션의 현재(리뉴얼 전) 사이드 메뉴 구성** (`src/ui/ui-side-menu.js`의
`MainSideMenu`/`SharedAppNavBlock`, `docs/renewal-baseline.md` §5에서 이미 실측):

```
Group 1: 사용자 매뉴얼(배너) / 캘린더 설정 / 기념일 설정
Group 2: 채팅(마지막 발신자 미리보기) / 정산(뱃지+마지막 날짜) / 갤러리(마지막 날짜) /
         장소(마지막 장소명) / 메모(마지막 제목 단어)
Group 3: 컨텐츠(지역축제/문화행사/스포츠)
Group 4: 보관함(구 히스토리)
Footer: 공유 / 설정
```

각 항목에 붙어있는 "마지막 미리보기 텍스트"(예: 채팅의 마지막 발신자, 정산 뱃지)는 리뉴얼
후에도 유지해야 하는 정보 밀도다 — 단순히 아이콘+라벨만 남기면 정보 손실이다.

## 3. 실제 프로덕션 기능 전체 인벤토리 (빠뜨림 방지용 체크리스트)

리뉴얼 중 아래 항목 중 하나라도 새 UI에서 재현되지 않으면 "기능 누락"이다. 각 항목은
실제로 존재를 확인한 파일과 함께 적는다.

### 3.1 캘린더

- 월간 그리드, 이전/다음/오늘 이동, 연월 선택 드롭다운 (`ui-calendar-core.js`)
- 날짜 셀: 오늘 표시(리플 애니메이션), 공휴일 빨간색, 참여자 색 점, 확정 일정 축제바(겹치는
  일정 여러 개 stacking 지원), 기념일 바(핑크, 별도 색 계열)
- 공휴일 라벨/날짜연도 텍스트가 640px 이상에서만 노출 (`app.css` `.day-corner-label`/`.date-year`)
- 날짜 클릭 → DateModal (섹션 3.2)
- 빈 일정(참여자·일정 없는 날짜) 클릭 → 간단 등록 시트 (참여자 추가/장소 등록/기념일 즉시 등록)
- 참석 가능일 등록: 드래그(PC) + 롱프레스(모바일)로 다중 선택

### 3.13 투표 (Poll) — 실제로 완성된 기능, 스텁 아님

- 생성/수정: 제목, 설명, 선택적 마감시각(datetime-local), 드래그로 순서 변경 가능한 다중
  후보(각 후보에 URL 첨부 가능) — `ui-event-modals.js`
- 투표: 후보별 투표, 마감시각 지나면 자동 마감
- 마감 후: 득표 1위 자동 계산(동률이면 전부 표시, 무투표면 표시 안 함) + 상단 고정 뱃지,
  미참여자 명단 넛지
- 헬퍼: `getCalendarPolls`, `getActivePollOptions`, `isPollClosed`, `getPollOptionVoterIds`,
  `formatPollDeadline` (`app-utils.js`/`app-domain-helpers.js`)
- 표시: `ui-calendar-core.js`의 "진행중 투표" 패널, 관리자는 `ui-admin-dashboard.js`에서 전체
  캘린더 투표 열람 가능
- 데이터 위치: `calendar.polls[]` (DateModal의 4개 탭과는 별개, 캘린더 레벨 데이터)
- 주의: `poll-sortable-row`/`poll-drag-handle` 클래스명이 참석자 행·정산 항목 등 무관한
  드래그정렬 리스트에도 재사용되니 실제 투표 UI와 혼동하지 말 것
- **마스터플랜 §5.9 반영 시 참고**: 이미 완성된 기능이므로 "응답이 필요한 작업" 섹션에 녹일 때
  기존 생성/수정/투표/마감 로직은 그대로 재사용하고 표시 위치만 옮기면 된다.

### 3.16 PWA/manifest (이미 버그픽스 완료 — 유지만 하면 됨, 리뉴얼과 무관)

`app-domain-helpers.js:1710-1798`. `kkot`/`cw`/`jhair`처럼 알려진 캘린더는 정적 매니페스트
파일(`manifest-kkot.json` 등)을 가리키고, 그 외 캘린더는 blob으로 동적 생성. 정적 파일을 쓰는
이유는 iOS Safari 버그 두 가지를 피하기 위해서다: (a) 이미 삽입된 `<link rel="manifest">`의
href만 바꾸면 iOS가 반영 안 함 →엘리먼트 자체를 새로 만들어 교체해야 함, (b) manifest의
`id`/`start_url`/`scope`가 절대경로가 아니면 iOS가 서로 다른 캘린더를 하나의 설치 아이콘으로
합쳐버림. `src/index.html`의 `<head>`에 React 로드 전 이 스위치를 처리하는 부트스트랩 스크립트가
있음.

### 3.17 검색 — 지금은 통합검색이 없다 (헤더 검색은 새로 설계해야 하는 신규 기능)

현재 검색은 기능별로 완전히 분리돼 있다: 대화 검색(`ui-chat-room.js`/`ui-misc.js`), 메모 검색
(`ui-memo-view.js`), 갤러리 검색(사진/링크/파일, `ui-chat-gallery.js`), 정산 검색
(`ui-event-modals.js`), 보관함/컨텐츠 검색(`ui-summary-gallery.js`), 날씨 지역 검색
(`ui-side-menu.js`). **일반 사용자를 위한 통합검색은 지금 전혀 없다** — 관리자 대시보드에만
있다(3.15). 즉 WP-01의 헤더 검색 아이콘(`ui-app-shell-v2.js`의 `TopHeader`)이 누르면 갈 곳은
"기존 검색 화면 재배치"가 아니라 **새로 설계해야 하는 통합검색 기능**이다 — 지금 WP-01 슬라이스는
이 아이콘을 눌러도 "더보기" 탭 플레이스홀더로만 보낸다 (섹션 4.2 참고). WP-06(기록) 또는 별도
WP에서 각 기능별 검색을 하나로 합치는 작업이 필요하며, 이건 마스터플랜에 명시적으로 없는
추가 설계 과제이니 다음 작업자는 이 문서를 통해 인지하고 별도 WP로 스코프를 잡을 것을 권장한다.

### 3.18 캘린더 전환 — 지금은 메뉴 안 전환 UI가 없다 (전부 URL/공유링크/PWA 아이콘 기반)

일반 사용자가 여러 캘린더를 앱 안에서 메뉴로 전환하는 UI는 **존재하지 않는다.** 각 캘린더는
고유 URL(`/share/<calendarId>/...`, `parseSharePathFromLocation`)이나 캘린더별로 설치된
PWA 아이콘(3.16)으로 각각 접근한다. `getCalendarShareUrl`/`getViewShareUrl`이 공유 링크를
만들어준다. 오직 관리자 대시보드만 한 화면에서 여러 캘린더를 오가며 볼 수 있는 선택 UI가 있다.
**마스터플랜 §4.2가 말하는 "브랜드/캘린더 전환/검색/더보기 헤더"의 "캘린더 전환" 부분도
검색과 마찬가지로 새로 설계해야 하는 신규 기능**이다 — 기존에 옮겨올 UI가 없다. WP-01
`TopHeader`는 지금 캘린더 이름만 표시하고 전환 기능은 없다.

### 3.19 기념일 마일스톤 모드 — 확인 완료 (4번째 타입 `dday`)

기념일 타입은 실제로는 4종류다: `yearly`(매년 반복)/`once`(단일 날짜, 윤력 지원)/`range`(축제성
다일 이벤트)에 더해 **`dday`** 타입이 따로 있고, 이 안에서 다시 `ddayMode`가 `'countdown'`
(D-Day 카운트다운, 예: D-100) 또는 `'milestone'`(날짜수 자동경과, 예: "100일째")로 갈린다
(`ui-event-modals.js` 267~375번 줄, 1190~1192번 줄 부근 — `[['countdown', 'D-Day
