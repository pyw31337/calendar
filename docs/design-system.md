# 모여라 캘린더 UI 디자인 시스템

작성 기준: 2026-09-12 (관리자 대시보드 포함으로 범위 확장)  
적용 범위: 사용자용 캘린더, 일정·참여자·장소·메모·갤러리·정산 화면, 공통 레이어팝업, **그리고 관리자 대시보드(`AdminDashboard`와 그 하위 화면)**

이 문서는 지금까지 요청된 디자인 원칙을 구현 가능한 규칙으로 고정한다. 새 화면은 먼저 공통 모듈을 찾고, 모듈의 props만으로 해결되지 않을 때만 같은 모듈을 베이스로 확장한다.

**2026-09-12: 관리자 대시보드를 적용 범위에 공식 포함.** 이전까지 관리자 화면은 이 문서의 적용 범위 밖이라고 명시돼 있었고(`src/app.css`의 `.admin-scope` 다크모드 리셋 블록 주석 참고), 그 결과 상태색(성공/확정/위험 배지 등)이 라이트 기본값·다크 오버라이드·`.admin-scope` 리셋 세 곳에 각각 리터럴 hex로 중복돼 있었다. 이를 시맨틱 토큰(`--surface-success`, `--surface-danger` 등, 2절 참고)으로 통합해 어드민도 같은 토큰 체계 위에서 관리되도록 정리했다. 새 관리자 화면을 만들 때도 사용자 화면과 동일하게 이 문서의 규칙을 그대로 따른다 — "관리자니까 대충"은 더 이상 허용하지 않는다.

이 개정은 Supabase(인터랙티브 요소 6~8px, 카드 12~16px처럼 radius를 역할별로 위계화하고 액센트 컬러를 한 곳에만 절제해서 쓰는 방식), Apple Human Interface Guidelines(여백을 계층을 만드는 도구로 명시하고, 타이포그래피 램프가 계층을 대신 말하게 하는 방식), 네이버페이 디자인 시스템 deFign(버튼·입력·리스트처럼 헷갈리기 쉬운 요소를 화면마다 재해석하지 않도록 공통 UI 라이브러리로 강제하는 방식)을 참고해서 우리 상황에 맞게 반영했다.

## 1. 시각 언어

- 외곽 둥근 사각형은 `--radius-md`(10px), 내부 중첩 박스는 `--radius-sm`(6px)을 사용한다. 액션 버튼은 캡슐형을 사용하지 않는다.
- 색상, 배경, 테두리, 그림자는 `src/app.css`의 토큰을 우선 사용한다. 컴포넌트 내부에서 같은 의미의 색상을 새로 하드코딩하지 않는다.
- 일반 본문은 `--text-main`, 보조 설명은 `--text-muted`, 비활성은 `--text-light`를 사용한다.
- 목록·입력·팝업은 카드 배경, 얇은 테두리, 8~16px 간격으로 계층을 만든다. 과도한 glow, 그림자, 애니메이션은 사용하지 않는다.
- 간격은 `--space-1`(4px)부터 `--space-10`(40px)까지의 4px 그리드 토큰만 사용한다. 한 컴포넌트의 형제 영역(모달의 header/body/footer, 카드의 title/content)은 같은 step을 공유하며, 14/16/18/20px처럼 비슷하지만 다른 값으로 흩어지지 않는다.
- 그림자는 `--shadow-sm`(목록 행, 얇은 카드) / `--shadow-md`(떠 있는 카드, 팝오버) / `--shadow-lg`(모달, 바텀시트)로 역할을 나눈다. 같은 계층 깊이에 서로 다른 그림자를 섞지 않는다.
- 성공/확정/위험처럼 의미가 고정된 상태색은 컴포넌트마다 리터럴 hex를 새로 적지 않고 시맨틱 토큰을 쓴다: `--surface-success`(가능일/전원가능), `--surface-confirmed`/`--border-confirmed`(모임 확정), `--surface-danger`/`--border-danger`/`--text-danger`/`--surface-danger-hover`(삭제·위험), `--border-confirmed-soft`/`--border-available-soft`/`--surface-available-soft`/`--border-success-soft`(날짜 리스트의 옅은 톤 변형), `--surface-hover-tint`(리스트 행 hover). 라이트/다크/관리자 세 화면 모두 이 토큰들이 자동으로 올바른 값을 낸다 — 다크모드나 관리자 전용 오버라이드를 selector 단위로 새로 추가하지 않는다.
- 참여자 퍼스널 컬러(`ParticipantBackdrop`), 기념일 색상 구분, 장소 카테고리 컬러, 방문지/방문예정 구분은 위 시맨틱 상태색 규칙과 별개다 — 각 항목이 곧 하나의 정체성을 나타내므로 고정 팔레트로 유지하고, 이 규칙에 맞춰 축소·통일하지 않는다.

## 2. 공통 모듈

| 개념 | 표준 모듈 | 사용 규칙 |
| --- | --- | --- |
| 참여자 표시 | `ParticipantBackdrop` | 퍼스널 컬러 circle + 굵은 컬러 이름. 선택 목록, 셀렉트 값, 요약, 카드에 동일 적용 |
| 셀렉트/백드롭 | `SimpleBottomSheetPicker` | 브라우저 native select 대신 하단 레이어. 카테고리 셀렉트와 같은 `form-select` 외형 |
| 추가/수정 액션 | `FormAddEditActionButtons` | 추가·수정·취소의 라벨과 44px 높이를 공통 처리 |
| 확인 | `ConfirmDialog` / `onRequestConfirm` | 삭제·수정·저장·복구 등 상태 변경 전 레이어 1회 확인. `window.confirm`, `alert`, `prompt` 금지 |
| 긴 입력 | `AutoGrowTextarea` | 내용량에 따라 자동 확장. 모바일에서 한 줄 고정으로 내용을 압축하지 않음 |
| 편집 선택 체크박스 | `EditSelectCheckbox` | 갤러리 링크/파일 카드 기준. 8px inset, 20×20, radius 5. 사진·썸네일은 `onMedia`, 흰 카드(장소)는 `onCard` |
| 페이지 헤더 | `PAGE_HEADER_*` | 보관함 헤더가 스펙. 뒤로 36×36 + `BackArrowIcon` 22, 검색 `SearchIcon` 20, 메뉴 `ThreeLinesIcon` 22, 색 `var(--text-muted)`, 아이콘 패딩 6px, 액션 gap 8px, 제목 0.95rem/800 |
| 목록 툴바 | `LIST_TOOLBAR_ROW_STYLE` | `전체\|일자` + 추가/편집 한 줄. padding `12px 0 4px`. 장소처럼 스크롤 밖이면 가로 16px를 덮어쓴다 (`12px 16px 4px`) |
| 편집 액션 줄 | `getListEditActionWrapStyle` / `getListEditTextBtnStyle` | 모바일 편집만 가로 100% (`전체\|일자` 숨김). PC는 내용 너비 + 오른쪽 정렬. 브라우저 50%로 늘리지 않는다. 텍스트 버튼 패딩 모바일 8px / PC 14px, `white-space: nowrap`이라 320px에서도 한 줄 |

공통 모듈을 직접 쓰기 어려운 화면은 동일한 class/token/높이/간격을 유지한 얇은 래퍼만 허용한다. 화면별 임의 셀렉트, 참여자 pill, 임의 확인창을 새로 만들지 않는다.

## 3. 버튼 규칙

- 추가·저장·수정·확인·취소·삭제는 최소 높이 44px, `btn` 계열, `--radius-md`를 사용한다.
- **예외: 관리자 대시보드의 밀도 높은 툴바 버튼.** 이 44px 규칙은 모바일 터치 타겟 기준으로 만들어졌다. 관리자 대시보드는 데스크톱 전용 스태프 도구이고, 한 화면에 여러 캘린더·통계·로그를 동시에 보여줘야 해서 Supabase류 대시보드처럼 32~36px의 더 조밀한 버튼이 실제로 더 적합하다. `AdminDashboard`/`ui-admin-modals.js`의 기존 32~36px 툴바 버튼은 이 규칙 위반이 아니라 의도된 예외로 취급한다 — 44px로 일괄 확대하지 않는다. 단, 삭제처럼 되돌리기 어려운 단일 확인 액션(모달의 최종 확인 버튼 등)은 예외 없이 44px를 지킨다.
- 버튼 가로는 세로 이상이어야 한다. 최소 비율은 가로:세로 1:1. 아이콘 전용은 정사각, 텍스트 액션(취소/붙여넣기/일괄공유 등)은 더 넓게 둔다. 모바일에서 패딩을 줄여 세로로 길쭉하게 만들지 않는다.
- 추가 버튼은 기존 회색 배경의 secondary 스타일을 우선 사용한다. 같은 “추가” 의미를 페이지마다 다른 높이·색·radius로 만들지 않는다.
- 삭제는 danger 스타일, 수정/저장은 dark 또는 primary 스타일, 취소는 secondary 스타일을 사용한다.
- 28~32px 아이콘 버튼은 순수 보조 조작(닫기, 월 이동, 휴지통 아이콘)에만 허용하며 텍스트 액션에는 사용하지 않는다.
- 버튼 안의 텍스트가 좁은 화면에서 여러 줄로 깨지지 않도록 `white-space: nowrap`을 적용하고, 필요한 경우 버튼을 세로로 쌓는다.

## 4. 입력·숫자·셀렉트

- 모든 금액, 계좌번호, 인원수, 숫자 전용 필드는 `inputMode="numeric"` 또는 `type="number"`를 사용한다.
- 모바일 입력 폰트는 16px 이상으로 유지하여 iOS 자동 확대를 막는다.
- 모든 셀렉트는 `SimpleBottomSheetPicker`를 우선 사용하며, 불가피한 native select도 `form-select` class와 동일한 chevron/높이/테두리를 사용한다.
- URL, 날짜, 일반 텍스트, 금액은 필드와 라벨을 분리해 의미를 혼동하지 않게 한다.

## 5. 모바일 레이아웃

- 모바일 기준 폭에서는 데스크톱의 2열·3열 폼을 한 줄 한 요소의 stack으로 전환한다.
- 제목·설명·목록 텍스트는 무리한 가로 압축보다 세로 흐름을 우선한다. 긴 텍스트는 자연스럽게 줄바꿈하고, 날짜/메타와 본문을 분리한다.
- 백드롭은 브라우저 하단에서 올라오며, 내용이 길면 내부만 스크롤한다.
- 팝업 본문은 화면 높이의 90%를 넘지 않고, footer 액션은 항상 접근 가능해야 한다.

## 6. 상태 변경과 확인

- 삭제, 마감, 복구, 저장, 수정처럼 데이터가 바뀌는 액션은 실행 전에 레이어 확인을 한 번만 노출한다.
- 확인 취소 시 데이터·팝업 상태를 변경하지 않는다. 확인 후에는 데이터 레이어에서 중복 확인하지 않는다.
- 검증 실패는 toast 또는 앱 레이어의 오류 메시지로 보여주며 시스템 `alert`를 사용하지 않는다.

## 7. 정산 특칙

- 정산 수정은 `일반`(타이틀~계좌번호)과 `정산`(일자별 지출·개인지출) 탭으로 분리한다.
- 수입은 `+`, 지출은 `-`로 표시한다. 정산 총 지출에는 수입을 포함하지 않는다.
- 개인지출은 기존 일정 정산내역과 같은 카드형 목록으로 보여주고, 일반 탭 참여자는 개인지출 등록 아래에 한 줄 가로 목록으로 보여주며 개인별 합계를 표시한다.
- 정산 목록은 진행 중인 최신 카드가 위, 마감된 과거 카드는 목록 레이어에서 확인한다.

## 8. 페이지 헤더

보관함 상단이 기준이다. 갤러리·장소·컨텐츠·메모·채팅·정산도 같은 모듈을 쓴다.

- 뒤로: `PAGE_HEADER_BACK_BTN_STYLE` (36×36 원, `BackArrowIcon` 22, `var(--text-muted)`). 채팅·메모·정산은 헤더가 숨어도 남는 플로팅 뒤로를 유지한다.
- 제목: `PAGE_HEADER_TITLE_STYLE` (0.95rem, fontWeight 800, 가운데 절대 배치).
- 검색/메뉴: `PAGE_HEADER_ICON_BTN_STYLE` (padding 6px, `var(--text-muted)`). 검색 아이콘 20, 메뉴 `ThreeLinesIcon` 기본 22. 페이지마다 다른 햄버거 path나 32px 원형 버튼을 만들지 않는다.
- 액션 묶음: `PAGE_HEADER_ACTIONS_WRAP_STYLE` (gap 8px). gap 2px/4px로 조밀하게 붙이지 않는다.

## 9. 편집 체크박스

모든 편집 모드 선택 체크박스는 갤러리 링크/파일 카드와 같다.

- 위치 `top/left: 8px`, 크기 20×20, `borderRadius: 5px`.
- 사진·썸네일·링크·파일·추억 칸: `EditSelectCheckbox variant="onMedia"` (어두운 칩 + 흰 테두리).
- 장소처럼 흰 리스트 카드: `variant="onCard"` (카드 배경 + 회색 테두리).
- 4px/6px inset, 22×22, 12/10 등 화면별 임의 좌표를 새로 두지 않는다.

## 10. 목록 툴바와 본문 패딩

- 툴바 한 줄(`전체|일자` 또는 `전체|방문|예정` + 추가/편집)은 `LIST_TOOLBAR_ROW_STYLE` — padding `12px 0 4px` (위는 넓고 아래는 얇다).
- 보관함·추억 본문 스크롤은 헤더 스택 실측 높이 + safe-area를 padding-top으로 쓴다. 하드코딩 118px를 쓰지 않는다.
- 장소 툴바는 스크롤 밖이므로 `12px 16px 4px`, 리스트 본문은 `8px 16px 16px`.
- 탭 숫자 뱃지는 `UnderlineTabs`의 `opt.badge`를 쓴다. 갤러리(사진/링크/파일)와 보관함(추억/인물/지난모임) 모두 텍스트 오른쪽에 같은 뱃지를 둔다.
- PC 편집 모드에서는 `전체|일자`(장소는 `전체|방문|예정`)를 그대로 둔다. 모바일에서만 숨겨 삭제/붙여넣기/일괄공유/취소가 한 줄에 들어가게 한다.
- 편집 텍스트 버튼은 `getListEditTextBtnStyle`: 높이 44px, 최소 가로 44px, 패딩 `0 8px`(모바일) / `0 14px`(PC). 브라우저 가로의 50%로 늘리지 않는다.

## 11. 포커스 상태

- 클릭 가능한 모든 요소(버튼, 카드, 리스트 행, 메뉴 아이템)는 키보드 포커스를 받을 때 `:focus-visible`로 눈에 보이는 상태를 표시한다 — 마우스 클릭에는 나타나지 않고 Tab 이동에만 나타나야 한다.
- 포커스 표시는 `outline`을 지우고 대체 표시(배경색 변화, 테두리 강조 등)로 바꾸는 경우에도 대비가 충분해야 한다. `outline: none`만 적용하고 대체 표시를 두지 않는 것은 금지한다.
- 새 인터랙티브 컴포넌트를 추가할 때는 기존에 이미 있는 `.admin-side-menu-item:focus-visible`, `.resizable-list-handle:focus-visible`, `.poll-voter-option:focus-visible` 같은 패턴을 참고해서 다크모드·관리자 화면에서도 대비가 유지되는지 확인한다.

## 12. 빈 상태·에러·로딩

성공 경로(데이터가 있고, 요청이 성공하는 경우)만큼 아래 세 상태도 화면 설계 시점에 같이 정의한다. 이 상태들은 지금까지 화면마다 있으면 만들고 없으면 비워두는 식으로 처리돼 왔고, 완성도 차이가 가장 크게 드러나는 지점이다.

- **빈 상태**: 목록이 비어 있을 때 빈 여백만 두지 않는다. 무엇이 없는지(예: "등록된 장소가 없어요")와, 가능하면 다음 행동(추가 버튼 위치 안내)을 함께 보여준다.
- **에러 상태**: 요청 실패는 `alert`/`console.log`로만 남기지 않고 화면에 원인을 짧게 설명하는 문구 + 재시도 동작을 둔다. "오류가 발생했습니다" 같은 모호한 문구 대신 무엇을 하다 실패했는지 말한다.
- **로딩 상태**: 목록/카드가 비어 보이는 순간이 있는 화면은 스켈레톤이나 스피너로 "지금 불러오는 중"임을 표시한다. 로딩 중과 빈 상태(데이터가 진짜 없음)를 같은 화면으로 착각하게 두지 않는다.
- 세 상태 모두 카드 배경(`--bg-card`)·본문 텍스트 토큰(`--text-muted`, `--text-light`) 위에서 구성하고, 별도의 색을 새로 정의하지 않는다.
